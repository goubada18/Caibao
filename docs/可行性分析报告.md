## 0. 结论摘要（TL;DR）

> 如果你的时间只够读一页，读这一页。

### 0.1 一句话结论

**项目可行，但原技术文档的核心技术方案有三处需要修正；真正的性能瓶颈不在「UI 树 vs 截图」，而在「每一步都要调模型」。推荐方案是 Fork 肉包的产品化层 + 重写感知/执行/加速三层，并把「轨迹复用」而不是「UI 树解析」作为一号提速手段。**

### 0.2 三处必须修正的技术判断

| # | 原文档判断 | 实际情况 | 影响 |
|---|---|---|---|
| 1 | 「`uiautomator dump` → 本地解析 XML」，感知速度 200–500ms | 实测 `uiautomator dump` **单次 2.2–2.8 秒**，且内部有 `waitForIdle`（默认最长等 10s），动画/信息流页面会超时报错甚至 SIGKILL | **照原方案做，感知会比截图+VLM 更慢**，目标直接落空 |
| 2 | 「用 `injectInputEvent` 物理注入替代 `input tap` shell 命令」，反检测能力大幅提升 | `input tap` 的底层**就是** `IInputManager.injectInputEvent`，二者机制完全相同。真实差距只有：省掉每次 fork 进程（约 150–400ms → 5–20ms）、可自定义 pressure/size/轨迹 | 「反检测大幅提升」是**被高估的收益**；真实收益是**延迟**和**轨迹可控性** |
| 3 | 「速度提升 5–10 倍」来自 UI 树替代 VLM | 单步耗时的大头是**模型推理**（云端 VLM 1–4s/步）。UI 树只省掉视觉编码，不省掉决策推理 | 5–10× 需要靠**跳过模型调用**（轨迹复用/宏/确定性匹配）才能拿到，不能靠换感知方式 |

### 0.3 最关键的外部发现

- **肉包官方 `roubao2.0+AccessibilityService` 分支已经在做「无障碍混合模式 + UI 树感知 + 宏脚本系统」，但最后一次提交停在 2025-12-14，已停滞约 9 个月。**
  这意味着：原文档规划的内容，上游想过、开过头、没做完。你不是从零创新，也不是在补空白——你需要回答的问题是**「为什么我能做完，而上游没做完」**（答案很可能是：上游是一个人用 AI 生成代码堆功能，缺乏验证闭环）。
- **Google Play 官方政策明确写道：Accessibility API「并非为执行以下功能而设，亦不得要求执行有关功能：……自动发起、规划和执行操作或做决定的应用程序」。**
  这几乎精确描述了本项目。**结论：本项目无法上架 Google Play**，分发渠道只能是 GitHub Releases / F-Droid / 自分发。对「冲 Star」目标影响不大（本来也靠 GitHub），但要在 README 显著位置说明。
- **HyperOS 存在「随机禁用已开启的无障碍服务」的已知问题**（社区为此专门做了 Magisk 模块 `hyperos-accessibility-fix`）。你的主力测试机正是小米 HyperOS。**这是本项目最大的单点风险**，必须在 POC 阶段先验证。

### 0.4 推荐方案（回答「基座怎么选」）

**推荐：Fork 肉包 v1.4.2 稳定主线，复用其「产品化层」，重写「感知层 / 执行层 / 加速层」。**

- **复用**：Material 3 UI、首启引导、Shizuku 集成、多 VLM 后端抽象、双语、悬浮窗与执行可视化、安全拦截、APK 发布流程。这些是肉包最值钱的资产，也是「冲 Star」最直接的加分项。
- **重写**：Agent 主循环、感知层、执行层。原文档的设计要按第 4 章修正后实施。
- **借鉴但不合入**：`roubao2.0+AccessibilityService` 分支。它的设计思路对，但代码停滞 9 个月、很可能是 AI 批量生成未经验证的产物，直接 merge 风险极高。**抄设计，抄命名，不要抄代码。**

详细论证见第 5 章。

### 0.5 建议的一号工程目标（不要一上来就做通用 Agent）

先做透 **3 类 App × 10 个高频任务**，把成功率做到可公开的数字，再谈通用性。原因见 9.1。

### 2.2 三条技术路线的实证数据

| 路线 | 代表项目 | AndroidWorld 成功率 | 单任务成本 | 说明 |

### 2.3 端侧推理可行性（直接决定 K60 Pro 能做什么）

| 数据源 | 环境 | 结果 |
|---|---|---|
| MNN + KleidiAI 官方 benchmark | Arm 移动端，Qwen2.5-VL-3B 4bit | 视觉编码 2.91s、prefill 266 tok/s、decode **44.96 tok/s** |
| 社区实测 | 骁龙 8 Gen 3 / 16GB，Qwen2.5-VL-3B Q4_K_M | 首 token 380ms、内存 2.1GB、**14 tok/s** |
| 社区实测 | 同环境，MiniCPM-V 2.6 Q4 | 首 token 310ms、内存 1.8GB、**18 tok/s** |
| MobiAgent phone_runner 官方要求 | 端侧部署 | **要求 8Gen3 或 8Elite + RAM ≥ 12GB**，模型 >1GB，跑在 Termux + MNN |

**对 K60 Pro（8 Gen 2）的判断**：

- 8 Gen 2 比 8 Gen 3 的 NPU/内存带宽低约一代，实测数据预计打 **6–7 折**：Qwen2.5-VL-3B Q4 大约 **8–10 tok/s**，视觉编码 **4–7 秒**。
- **结论：端侧可以做，但不能做主决策。** 可行定位是：
  - ✅ 端侧 **Grounder**（只做「这个按钮在哪」，输出 9.7 token 的紧凑 JSON，AgentCPM-GUI 就是这个设计）
  - ✅ 端侧 **离线降级 / 隐私模式**卖点
  - ❌ 端侧 **Planner / Decider**（一步步推理，每步 8–10 tok/s 会慢到不可用）
- **默认路径仍应为云端 VLM**，端侧作为可选增强。这也符合「冲 Star」——隐私卖点要有，但不能拖累主线体验。

## 3. 对原技术方案的逐条审视

> 这一章是本次调研最有价值的部分。以下每条都基于可查证的实测数据，不是主观意见。

### 3.1 ❌ 感知层：`uiautomator dump` 的性能预期是错的

**原文档**：「用 `uiautomator dump` 替代截图→VLM，速度提升 5–10 倍，单步感知 200–500ms」

**实测数据**：

| 来源 | 数据 |
|---|---|
| andykong.org《Fast automated mobile E2E testing》(2026-05) | `adb shell uiautomator dump` **~2.2s/次**，动画期间偶发 SIGKILL；Android 密集页面 2–3s |
| CSDN 实测对比 | 原生 `uiautomator dump` **平均 2.8s**，节点完整度仅 75% |
| uiautomator 源码机制 | 内部调用 `uiAutomation.waitForIdle(1000, 1000*10)`，**默认最长等待 10 秒**；持续更新的视图（信息流、弹幕、加载动画）会直接报 `ERROR: could not get idle state` |

**问题本质**：`uiautomator dump` 每次调用都要**冷启动一个 UIAutomator 客户端进程**，遍历完整无障碍树，还要等界面「静止」。在抖音/小红书这种永远在动的信息流页面，它甚至可能直接失败。

**修正方案（三选一，按推荐度排序）**：

| 方案 | 耗时 | 依赖 | 评价 |
|---|---|---|---|
| **A. 自研 AccessibilityService** | **< 100ms**（进程内 `getRootInActiveWindow()`） | 用户手动授权无障碍（可用 Shizuku 自动开启） | ★★★★★ **推荐主路径**。实时、无 idle 等待、可被动监听事件流 |
| **B. 常驻 uiautomator2 server** | **~200ms** | Shizuku 启动 `app_process` 常驻进程 | ★★★★☆ **推荐备选**。规避无障碍授权，openatx 已验证多年 |
| C. 每次 `uiautomator dump` | 2200–2800ms | 无 | ❌ 不采用 |

> **方案 B 的实现要点**：`app_process` + `new Instrumentation().getUiAutomation()` 是社区成熟技巧（openatx/uiautomator2 即如此）。Shizuku 的 `UserService` 以 shell 身份运行 Java 代码，`Shizuku.newProcess()` 可以 shell 身份起进程——两者都能承载这个常驻服务。**这是一条完全绕开 AccessibilityService 父条款的技术路径，对合规有额外价值（见第 8 章）。**

### 3.2 ⚠️ 执行层：`input tap` 与 `injectInputEvent` 的关系被误解

**原文档**：「用 `INJECT_EVENTS` 物理事件注入替代 `input tap` shell 命令，反检测能力大幅提升」

**事实**：Android 的 `input` 命令源码中，`input tap` 最终调用的就是 `IInputManager.injectInputEvent()`。**两者是同一条内核路径，注入的事件在 InputDispatcher 看来没有本质区别。**

**真实差异只有三点**（仍然值得做，但收益要如实表述）：

| 维度 | `input tap`（shell） | 进程内 `injectInputEvent` | 真实收益 |
|---|---|---|---|
| 进程开销 | 每次 fork 新进程 **150–400ms** | Binder 直调 **5–20ms** | ✅ **显著**（单步省 200ms+） |
| 事件参数 | pressure/size 为固定默认值 | 可自定义 pressure、size、toolType、轨迹插值 | ✅ **中等**（可靠性提升为主） |
| 反检测 | — | 无本质区别 | ❌ **被高估** |

**额外重要发现**：AccessibilityService 提供了第三条路径，而且在多数场景下**比注入更好**：

| 执行方式 | 耗时 | 优点 | 缺点 |
|---|---|---|---|
| `AccessibilityNodeInfo.performAction(ACTION_CLICK)` | 10–50ms | **最稳定**，不依赖坐标，界面滚动/分辨率变化都不影响 | App 若屏蔽无障碍则完全失效 |
| `AccessibilityService.dispatchGesture()` | 数十 ms | 走真实手势通道，能过绝大多数坐标校验 | 部分 ROM/长手势有限制（Android 13+ 有明显收紧） |
| `InjectInputEvent`（Shizuku） | 5–20ms | 通用，不依赖无障碍 | 需要 Shizuku；坐标依赖 |

**修正后的执行层策略：三通道按优先级降级**
1. 首选 `performAction`（有节点、且节点可操作时）
2. 降级 `dispatchGesture`（需要真实手势时）
3. 兜底 `injectInputEvent`（无障碍不可用/被屏蔽时）

> 社区实测佐证：某支付 App 自动化案例中，Appium（UiAutomator2）元素定位失败率 37–41%，改用原生无障碍服务后，捕获关键节点耗时 **87ms**，稳定性 >99.2%。

### 3.3 ❌ 「速度提升 5–10 倍」的来源被误判

单步耗时的真实构成（云端 VLM 方案的典型值）：

```
截图/感知         ~300ms   ──┐
视觉编码 + 推理   1.5–4.0s  ──┤ ← 真正的瓶颈在这里（70–85%）
执行点击          ~50ms     ──┘
```

把感知换成 UI 树，只省掉「视觉编码」那部分，**决策推理一步没少**。所以：
- 只换感知：单步 2.5s → 1.8s，约 **1.4×**
- 换感知 + 小模型/结构化输入：约 **2–3×**
- **要拿 5–10×，必须跳过模型调用本身。**

**这是全局最重要的判断：真正的提速杠杆是「不调用模型」。**

对应三个手段：

| 手段 | 参考 | 预期收益 | 工程量 |
|---|---|---|---|
| **轨迹复用 / 宏回放** | MobiAgent AgentRR：动作复用率 **60–85%**，复杂任务性能提升 **2–3×** | ★★★★★ | 中 |
| **确定性匹配**（resource-id/文本直接命中目标，不调模型） | DroidRun / AutoJs 思路 | ★★★★☆ | 低 |
| **快捷路径**（DeepLink / Intent / 系统 API 直达） | 肉包现有 Delegation 模式 | ★★★★☆ | 低 |

> MobiAgent 的数据支撑：真实使用中 **80% 的请求集中在 20% 的高频任务**上——这正是轨迹复用能生效的前提。原文档的「宏脚本系统」想法是对的，但只放在 v2.0 roadmap 里当附属功能，**应该把它提到架构核心层**。

### 3.4 ⚠️ 「反检测」预期需要下调，并重新定义

**必须诚实面对的三点**：

1. `input tap` 与 `injectInputEvent` 同源 → 换掉它不会带来质变。
2. 事件注入的物理特征（pressure/size/抖动）在当前 Android 版本中，**大多数 App 根本没有读取**。真正会被检测的是：无障碍服务是否开启（`Settings.Secure` 可读）、是否处于调试态、是否 root、点击的统计特征（间隔方差过小）、以及是否来自非前台进程。
3. 主流 App 的反自动化是**多因子、服务端、持续演进**的。客户端做得再像人，服务端行为分析（频次、路径、时段）仍然能识别。**这是打不赢的军备竞赛。**

**建议重新定义为「操作自然度」，服务于可辩护的目标**：

- ✅ 避免因操作过快导致的**事件丢失、误触、界面未加载完就点击**（这是真实的可靠性问题）
- ✅ 避免因高频操作触发 App 的**通用限流**（这是正常的工程问题）
- ✅ 提升录屏演示的观感（这是产品问题）
- ❌ 不宣称可绕过任何 App 的风控系统
- ❌ 不绕过验证码、人脸、短信、设备校验

**关于原文档 `Humanizer` 模块**：保留，但把「±5px 偏移 + 200–800ms 随机延迟」改为**可配置 + 分场景**。系统设置类任务不需要拟人化，内容浏览类任务才需要。固定 200–800ms 反而会让整体任务变得很慢——总耗时 = 步数 × 平均 500ms，20 步就是 10 秒纯等待。

### 3.5 ⚠️ 与肉包官方 v2.0 分支高度重合

**发现**：`Turbo1123/roubao` 的 `roubao2.0+AccessibilityService` 分支（最后提交 **2025-12-14**，commit message: `feat: 无障碍服务混合模式 + 宏脚本系统`，标注 Co-Authored-By: Claude Opus 4.5）已经在做：

- 无障碍服务混合模式（元素索引点击优先，失败回退坐标模式）
- UI 树感知（识别可点击元素、输入框、滚动区域，给 LLM 提供结构化上下文）
- 宏脚本系统（录制、存储、回放操作序列，支持循环播放、延时控制）
- 设置增强（无障碍开关与引导、混合模式状态展示）

**这几乎就是原文档规划的内容。**

**如何解读**：

| 解读 | 含义 |
|---|---|
| ✅ 好消息 | 方向被上游验证过，不是空想；你可以直接借鉴其设计决策与命名 |
| ⚠️ 坏消息 | 「做 UI 树 + 无障碍 + 宏」**不构成差异化**，因为上游已经宣布了（即使没做完） |

## 4. 平台与政策约束

### 4.1 Google Play 上架：不可行

Google Play 官方政策原文（[Permissions and APIs that Access Sensitive Information](https://support.google.com/googleplay/android-developer/answer/9888170)）：

> The Accessibility API is not designed and cannot be requested for:
> - remote call audio recording
> - **an app that autonomously initiates, plans, and executes actions or decisions**

**「自主发起、规划和执行操作」正是本项目的定义。** 因此：

| 结论 | 说明 |
|---|---|
| 上架 Google Play | ❌ 基本不可能（除非定位为真正的无障碍辅助工具并接受严格审核） |
| 上架国内应用商店 | ⚠️ 同样风险高（国内对无障碍权限管控更严） |
| **推荐分发** | ✅ GitHub Releases（肉包就是这么做的）+ F-Droid + 社群传播 |

**这对「冲 Star」反而是好事**：目标用户本来就在 GitHub。但要在 README 显著位置写明分发性，避免用户反复问「为什么商店搜不到」。

**顺带的技术红利**：如果能做到**完全不依赖 AccessibilityService**（走 Shizuku + 常驻 uiautomator2 server 路线），就绕开了这条政策。建议把它作为「降级模式」实现——默认走无障碍（体验最好），可选走 Shizuku 纯注入模式（合规更干净）。这本身也是一个可选的宣传点。

### 4.2 微信的特别风险（必须知情）

微信是目前国内**反自动化最强**的应用，技术层面的事实：

- 大量使用 `SurfaceView` / `TextureView` 绕过 View 绘制管线 → 控件树无法获取
- APK 中 `android:accessibilityTraversalEnabled="false"` → 系统拒绝注入 `AccessibilityNodeInfo`
- Android 10+ 对微信进程施加隐私敏感标记，强制关闭 `importantForAccessibility`
- 结果是 `dumpWindowHierarchy()` 返回空/仅顶层容器，**截图能用但控件树几乎拿不到**

**非技术风险（更重要）**：

> ⚠️ **自动化操作微信违反《微信个人账号使用规范》，可能导致账号限制或封禁。** 这是你的账号风险，不是技术问题。

**建议**：
1. 微信**不作为首期目标**。先把内容类/效率类/系统类做透。
2. 后续若要支持，做成**显式 opt-in + 首次启用时的风险告知 + 默认关闭**。
3. 微信场景只能走**纯视觉路线**（截图 + VLM），成功率预期要显著下调，README 里如实说明。
4. 金融功能（支付、转账、红包、收款、理财）**硬编码排除**，不可配置开启。

### 4.3 HyperOS / 小米设备的专项风险（你的主力机！）

| 风险 | 表现 | 来源 | 缓解 |
|---|---|---|---|
| **无障碍服务被随机禁用** | 切换省电模式、锁屏、force-stop 后立即失效 | 社区专门做了 Magisk 模块 `hyperos-accessibility-fix` 来对抗 | 前台服务 + 状态轮询 + 自动重连；Root 后可装该模块 |
| **神隐模式** | 非白名单应用每小时唤醒限制约 5 次 | MIUI 后台策略 | 首启引导用户加入白名单 |
| **MIUI 优化** | 部分机型需关闭「MIUI 优化」才能解除自动化限制 | 开发者社区 | 首启引导中检测并提示 |
| **电池优化** | 未加白名单 → 后台被杀 | Android 9+ 通用 + 厂商加成 | `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + 手动引导 |
| **多任务锁定** | 未加锁 → 一键清理即死 | MIUI/HyperOS | 引导用户在最近任务中锁定 |

**这条风险严重到需要在 POC 第一天就验证。** 如果 HyperOS 上无障碍服务撑不过 30 分钟，整个「无障碍优先」的架构就要改成「Shizuku + 常驻 dump server 优先」。

## 5. 选型建议

### 5.1 四个候选方案对比

| 方案 | 工作量 | 风险 | 差异化 | 适合度 |
|---|---|---|---|---|
| **A. Fork 肉包，重写感知/执行/加速** | 中（4–6 周 MVP） | 中 | 中高 | ★★★★★ **推荐** |
| B. 参考 DroidRun 思路完全自建 | 高（10–14 周） | 中高 | 高 | ★★★☆☆ |
| C. 基于 MobiAgent 思路（端侧 + 训练） | 很高（6 个月+） | 高 | 很高 | ★☆☆☆☆ 单人不可行 |
| D. 直接贡献肉包上游 | 低 | 低 | 低 | ★★☆☆☆ 拿不到自己的 Star |

**为什么不是 B（完全自建）**：肉包的「产品化层」（Material 3 UI、首启引导、多模型后端、双语、安全拦截、发布流程）是实打实的工程量，且恰好是「冲 Star」最需要的部分。扔掉它重写 UI 是净亏损。

**为什么不是 C（MobiAgent 路线）**：它的数据收集流水线 + 模型训练门槛，单人项目扛不住。而且端侧 7B 在 8 Gen 2 上跑不动主决策。

### 5.2 推荐方案详述

> **Fork 肉包 v1.4.2 主线，保留「产品化层」，重写「感知层 / 执行层 / 加速层」，新增「记忆层」。**

**保留（肉包现有资产）**
- Material 3 UI / 首启引导 / 双语 / 执行历史
- Shizuku 集成与授权流程
- 多 VLM 后端抽象（Qwen / GPT / Claude / Ollama）
- 悬浮窗、执行可视化、敏感页检测
- APK 构建与 GitHub Releases 流程

**重写**
- Agent 主循环（改为「计划一次、执行多步」而非「每步都推理」）
- 感知层：统一 `ScreenState` 抽象，多 Provider 融合
- 执行层：三通道降级执行器
- Prompt 与动作空间

**新增**
- **记忆层**：`ActTree` 轨迹存储 + 相似度匹配 + 回放（一号提速手段）
- 确定性匹配器：resource-id / 文本 / 内容描述直接命中，跳过模型
- 机型适配引导：检测 HyperOS/MIUI/ColorOS 并给出对应设置引导

**借鉴但不合入**
- `roubao2.0+AccessibilityService` 分支：抄设计与命名，代码只做参考

## 8. 合规与法律边界

### 8.1 硬边界（架构层面强制，不可配置）

| 类别 | 处理 |
|---|---|
| 支付宝 / 网银 / 证券 / 任何支付类 App | **包名硬编码拒绝**，不可通过配置开启 |
| 微信金融功能（支付、转账、红包、收款、理财） | **硬编码拒绝**，不可开启 |
| 密码输入框（`isPassword=true`） | 拒绝自动填充 |
| 验证码 / 人脸 / 短信校验 | 不绕过；触发时转**人工接管** |
| 登录/设备校验 | 不绕过；转人工接管 |

### 8.2 设计原则

- **默认白名单而非黑名单**：用户显式授权哪些 App 可被自动化，而不是「除了黑名单都行」
- **敏感操作二次确认** + **全程可中断**（肉包已有悬浮窗中止，保留并强化）
- **不采集、不上传**用户屏幕内容到除用户自己配置的 VLM 之外的任何地方
- **README 显著位置**：说明本项目性质、所需权限、不得用于的用途、分发方式

### 8.3 需要知情的风险

- **微信自动化违反其用户协议**，存在账号限制/封禁风险 → 见 4.2
- **自动化操作可能导致误操作**（误发消息、误下单、误删数据）→ 必须有「执行前预览 + 逐步确认」模式
- **无法上架应用商店** → 见 4.1
- **第三方 App 界面变更**会导致既有轨迹/宏失效 → 记忆层必须有失效检测与自动重录

### 8.4 我不会参与的部分（明确说明）

为保证项目长期可持续，以下内容不在本次方案范围内，且后续也不会提供：

- 针对任何金融/支付 App 风控系统的对抗或绕过
- 绕过验证码、人脸识别、短信验证、设备指纹
- 用于刷量、刷赞、薅羊毛、批量注册、群控的自动化
- 任何形式的账号批量控制

「操作自然度」模块的设计目标严格限定在**提升自动化可靠性、避免误触、避免触发通用限流**，不宣称、不追求反检测效果。

## 9. 分阶段实施路线

### 9.1 一号工程目标：先做窄，再做宽

**首期只做 3 类 × 10 个任务**，把成功率做成可公开的数字：

| 类别 | App | 任务示例 |
|---|---|---|
| 系统类 | 系统设置、文件管理、通知栏 | 开关 WiFi/蓝牙、调整亮度、清理通知、打开指定设置项 |
| 内容类 | 小红书、B站、微博 | 搜索关键词、打开指定笔记/视频、点赞/收藏、关注用户 |
| 效率类 | 高德地图、日历、闹钟 | 搜索地点并导航、新建日程、设置闹钟 |

**为什么先窄后宽**：
1. 通用 Agent 的成功率在当前技术水平下**做不出好看的数字**，而可验证的数字才是开源项目的信任基础
2. 10 个任务足以暴露全部架构问题（感知、执行、降级、记忆）
3. 完成后可发布「10 个真实任务成功率 XX%」——这是别人没有的东西

### 9.2 阶段划分

| 阶段 | 目标 | 关键产出 | 估计工期（单人，业余） |
|---|---|---|---|
| **S0 POC** | 跑完 7 项 P0 验证 | `POC-报告.md` + 架构定稿 | 1–1.5 周 |
| **S1 地基** | Fork、编译、跑通原功能；接入自有 AccessibilityService；三通道执行器 | 可真机运行的最小闭环（硬编码任务） | 1.5–2 周 |
| **S2 感知+决策** | `PerceptionHub` 融合；Prompt 与动作空间；确定性匹配器 | 支持自然语言指令，10 个任务能跑通 | 2–3 周 |
| **S3 加速+记忆** | `ActTree` 录制/匹配/回放；失效检测 | 高频任务耗时下降 50%+ | 2 周 |
| **S4 安全+体验** | Guard 层；机型适配引导；执行轨迹可视化；演示录制 | 可发布的 v0.1 | 1.5 周 |
| **S5 发布** | README、演示 GIF/视频、测试报告、Release APK | GitHub 公开发布 | 0.5 周 |
| **合计（MVP）** | | | **约 9–12 周** |
| **S6 增强**（可选） | 端侧 Grounder、宏编辑 UI、微信（opt-in）、更多 App | | 后续 |

> 排期假设：单人、业余时间投入、Android 开发有一定基础。**若 P0-2（HyperOS 无障碍存活）不通过，S1–S2 需额外 2 周改造为 Shizuku + U2 路线。**

### 9.3 优先级排序（如果时间不够，按此砍）

1. ✅ **必做**：POC、AccessibilityService、三通道执行、Guard、10 个任务跑通、README + 演示
2. ⚠️ **应该做**：ActTree 记忆层（一号提速手段）、机型适配引导、轨迹可视化
3. 🔵 **可选**：端侧 Grounder、宏编辑 UI、多语言、微信支持、定时任务

## 10. 验收指标（可测量）

> 定义清楚「做成什么样算成功」，避免无止境打磨。

### 10.1 性能指标

| 指标 | 当前基线（肉包） | 目标 | 测量方式 |
|---|---|---|---|
| 单步延迟（记忆命中） | 不存在 | **< 150ms** | 打点统计 p50 |
| 单步延迟（确定性匹配） | 不存在 | **< 250ms** | 打点统计 p50 |
| 单步延迟（模型决策） | 2–5s | **p50 < 2.5s，p95 < 4s** | 打点统计 |
| 10 任务平均总耗时 | 待测（先建基线） | **下降 40%+** | 与肉包原版对比 |
| 高频任务动作复用率 | 0 | **≥ 50%**（MobiAgent 参考值 60–85%） | ActTree 命中统计 |

### 10.2 成功率指标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 系统类任务成功率 | **≥ 90%** | 每任务跑 10 次 |
| 内容类任务成功率 | **≥ 75%** | 每任务跑 10 次 |
| 效率类任务成功率 | **≥ 70%** | 每任务跑 10 次 |
| 无障碍服务 30 分钟存活率（HyperOS） | **100%** | 前台/锁屏/省电切换 |
| 敏感操作拦截准确率 | **100%**（宁可误拦） | 构造 20 个敏感场景 |

### 10.3 项目影响力指标（对应「冲 Star」目标）

| 指标 | 3 个月目标 |
|---|---|
| GitHub Star | 先不设数字，先做到「README 有说服力」 |
| 可复现资产 | ✅ 10 任务成功率报告 + 录屏 + POC 原始数据 |
| 中文 App 覆盖清单 | 公开一份「XX 个主流中文 App 控件树可解析性普查表」 |

> 说明：**第三项「中文 App 控件树可解析性普查表」是你最容易建立、也最稀缺的差异化资产。** 国际上没有任何项目做过这件事，而它对每一个做移动端 Agent 的人都有用。强烈建议把它做成一份独立的、持续更新的公开文档。

## 11. 风险登记表

| ID | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | **HyperOS 随机禁用无障碍服务** | 高 | 高 | P0-2 先验证；前台服务 + 轮询自愈；备选 Shizuku+U2 路线；Root 后可装 `hyperos-accessibility-fix` |
| R2 | 目标 App 主动屏蔽控件树 | 高 | 中 | P0-4 普查；混合感知，视觉兜底；公开可解析性表 |
| R3 | 云端 VLM 延迟/成本超预期 | 中 | 中 | P0-6/P0-7；2K 降采样；模型可切换；记忆层降调用量 |
| R4 | 端侧推理在 8 Gen 2 上不实用 | 中高 | 低 | 端侧仅做可选 Grounder，不影响主线 |
| R5 | 肉包 v1.4.2 代码质量差 / 无法编译 | 中 | 中 | POC 阶段先完成一次完整编译 + 真机跑通 |
| R6 | 项目与肉包 v2.0 分支重合，缺乏差异化 | 高 | 中 | 差异化建立在「可验证的成功率数字 + 中文 App 普查表 + 工程质量」，而非功能清单 |
| R7 | 微信封号风险 | 中 | 高 | 首期不做；后续 opt-in + 风险告知；金融功能硬排除 |
| R8 | 合规质疑（无障碍权限滥用） | 中 | 中 | 严格遵守第 8 章；README 显式声明；不宣称反检测 |
| R9 | 单人项目精力不继（上游已示范过） | **高** | 高 | 严格按 9.3 砍范围；MVP 目标锁定 9–12 周；每阶段都有可发布物 |
| R10 | 第三方 App 更新导致轨迹失效 | 高 | 中 | 记忆层必须有失效检测 + 自动重录 + 版本标记 |

> **R9 是本项目最大的隐性风险。** 肉包 v2.0 分支的停滞就是前车之鉴。建议：把 MVP 拆成 6 个可独立发布的里程碑，每完成一个就推 GitHub——即使中途停摆，也有可展示的成果。
